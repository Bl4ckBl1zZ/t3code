Cross-provider handoff

Switching a started thread to another provider used to be blocked — the provider's resume state is driver-specific, so a new session would start with no memory. Now the outgoing model writes a handoff summary first, the summary is recorded in the timeline, and the incoming model picks the conversation up from it. Same thread, in place.

What happens server-side

  1. Client dispatches thread.handoff.start — the only new client command.
  2. Decider records pending state on the existing thread.meta-updated event. Rejects if a turn is running, a handoff is already pending, or the thread never started.
  3. Reactor asks the live session for a summary via sendTurn. HandoffSummaryCapture diverts that turn's runtime events so nothing reaches the timeline.
  4. Fallback if needed textGeneration.generateHandoffSummary over the stored transcript.
  5. Activity + swap appends provider-handoff, stops the old session, then thread.handoff.complete swaps modelSelection and stores pendingHandoffContext.
  6. Next turn injects it the decider moves the context onto the turn event and clears it in the same batch — no double-injection on retry.

Guarantees

  • Zero memory loss is best-effort, not blind. The live session is preferred because it still holds full tool output and file contents the transcript can't show.
  • The summarization turn is invisible. No assistant message, no session-status churn. An approval request fails the capture rather than blocking on a prompt nobody can see.
  • Your message is never rewritten. The context block is prepended to the provider input only; the persisted user message stays exactly what you typed.
  • If both summarizers fail, the switch does not happen. You keep a working session instead of a new provider with amnesia, and a failure row explains why.
  • No new event types. OrchestrationEvent is a closed union clients decode, so this rides on optional fields — old clients ignore them.
